# 短剧分集剧本写作

将用户已经确认的故事事实转换为可拍摄、可表演、具有因果推进的分集剧本。默认使用中文；如果用户明确指定语言、平台或格式，按用户要求输出。

## 适用边界

- 只撰写或修改分集剧本，不擅自重新设计故事梗概、主线大纲、世界观或人物设定。
- 不直接生成分镜表、绘画提示词、视频生成提示词或其他下游制作文件，除非用户另行提出并且任务已明确切换。
- 用户已确认的锁定事实和禁止事项不可修改、绕过或弱化。
- 当输入事实互相冲突时暂停写作，先列出冲突位置、涉及事实、无法同时成立的原因，以及需要用户确认的选项。
- 当缺少会明显影响剧本结果的关键信息时，先提问；不要用未经授权的猜测填补关键事实。可对不影响剧情的次要表达作最小化处理。
- 用户本次明确的修改要求优先于本技能的一般建议，但不得突破用户明确给出的锁定事实和禁止事项。

## 写作前需要确认的信息

尽量从用户提供的材料中读取以下内容：

- 项目名称、题材类型、目标平台（如有）。
- 当前集数、单集目标时长和语言。
- 已确认的故事梗概与主线大纲。
- 当前集分集蓝图。
- 人物姓名、身份、欲望、性格、关系和当前状态。
- 上一集结束时的人物状态。
- 当前集目标、阻力、人物选择、局部结果和结尾压力。
- 不得修改的锁定事实、禁止出现的内容。
- 场景数量、演员数量、拍摄成本或制作方式等限制；只有用户提供时才启用，不自行假设。

## 工作流程

### 1. 检查输入一致性

检查人物、时间线、关系、动机、空间和锁定事实是否完整一致。发现冲突时停止写作并明确说明：

1. 冲突发生在哪里；
2. 涉及哪些事实；
3. 为什么它们不能同时成立；
4. 需要用户确认什么。

不得暗中修正设定。

### 2. 建立本集戏剧任务

在内部先明确以下问题，再开始写场景：

- 观众本集主要跟随谁；
- 主角本集想得到什么；
- 谁或什么真正阻止主角；
- 主角做出了什么选择；
- 选择造成了什么结果和代价；
- 集末权力、信息、关系、资源、危险、位置或行动方向发生了什么变化；
- 下一集的新压力从哪里产生。

### 3. 设计场景

每个场景至少完成一种可识别的戏剧作用：推进目标、增加阻力、揭示新信息、改变关系、迫使选择、产生阶段性结果，或为后续转折埋下伏笔。删除只解释背景、重复信息或没有行动后果的闲聊场景。场景之间应有因果连接，上一场的行动或信息要影响下一场。

### 4. 撰写可拍摄正文

- 优先写观众能看见或听见的动作、物件、环境、停顿、反应和选择。
- 不写大段文学化心理描写；表达内心时优先使用动作、选择、停顿、潜台词或人物反应。
- 只有用户明确允许时才使用旁白或内心独白。
- 对白要符合人物身份、关系和当下情绪；避免让角色说出双方已知、只是为了向观众解释剧情的信息。
- 使用已确认的人物姓名，不用“主角”“反派”“神秘人”等占位称呼代替确定角色。
- 反转必须有此前的信息、物件、行为或选择铺垫。
- 关键结果应由人物选择和既有事实造成，不能依靠突然出现的救援、新证据或对手无故自曝。
- 遵守用户提供的时长、平台和制作限制；没有提供的限制不自行添加。

### 5. 交付前质量门禁

交付前逐项检查并直接修订发现的问题：

- 开场是否尽快进入事件、冲突或悬念；
- 主角是否有明确的当集目标；
- 场景是否具有因果关系且各自承担戏剧作用；
- 中段压力是否持续升级，而不是反复同一种争吵、误会或打脸；
- 本集是否产生真实的局部结果；
- 集末是否至少改变权力、信息、关系、资源、危险、位置或行动方向中的一项；
- 结尾钩子是否来自本集事件；
- 人物语言是否有区分度；
- 是否符合时长、平台和制作限制；
- 是否严格遵守锁定事实与禁止事项。

发现问题时先改稿再交付，不只报告问题。

## 输出规则

默认输出完整分集剧本，并包含本集摘要和状态变化。详细字段、场景格式和示例见 [references/script-format.md](references/script-format.md)。

如果用户要求“只输出剧本正文”或等价要求，只输出场次正文，不输出创作过程、分析说明、质量检查、摘要或状态变化。

若用户只要求修改已有剧本，保留未被要求修改的内容和既有格式；修改后仍执行锁定事实、连续性和可拍摄性检查。

## 跨平台调用约定

本技能只依赖用户提供的文本事实和通用 Markdown/YAML 文件，不依赖特定平台 API、模型名称或本地路径。其他平台调用时，将用户材料直接作为输入，并按本文件的冲突处理、写作和输出规则执行；若目标平台不支持引用文件，先读取并合并 `references/script-format.md` 的相关格式要求。
